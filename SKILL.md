# Agentic Usage Analysis

Анализ работы ИИ-агентов над конкретным репозиторием по их локальным логам. Воркфлоу
отработан на реальном кейсе (Unity-репозиторий, 4 инструмента, месяц разработки): сбор
метаданных → извлечение → количественная статистика → дайджесты → качественный разбор
субагентами → кросс-сверка escaped defects → глубокий причинный синтез → итоговый отчёт.

Структура скилла:

- `references/storage-layouts.md` — карта хранилищ восьми инструментов и приёмы работы
  с неизвестными форматами. Читай перед Фазой 0/1 и при любом расхождении с реальностью.
- `references/subagent-prompts.md` — готовые промпты субагентов для Фаз 3–4.
- `references/report-template.md` — обязательная структура итогового отчёта (Фазы 5–6).
- `evals/evals.json` — тест-промпты для проверки скилла.

## Запуск

Все скрипты параметризованы. Общие аргументы:

- `--repo` — путь к анализируемому репозиторию (обязательный; соответствие сессии
  определяется по рабочей директории сессии: точное совпадение или вложенность).
- `--out` — рабочая папка результатов (по умолчанию `agentic-audit` в текущей директории;
  не создавайте её внутри репозитория без разрешения владельца — объём данных десятки МБ).
- `--db` / `--root` — переопределение путей хранения конкретного инструмента.

Скрипты Python 3.10+, зависимостей нет (sqlite3 — стандартная библиотека; matplotlib
нужен только для графиков, скрипт падение переносит). Пути рассчитаны на Windows +
Git Bash (проверено), но написаны через `os.path`/`Path` — переносятся; на Linux учти,
что сопоставление путей чувствительно к регистру (`os.path.normcase` там — no-op).

**Приватность.** Дампы содержат полные тексты пользователя и аргументы shell-команд —
а там встречаются токены, ключи и пароли, которые агенты когда-то вбивали в команды.
Папку `<OUT>` не публикуй и не копируй наружу без санитайза; цитаты из дампов перед
включением в отчёт проверяй глазами; отчёт не коммить без решения владельца.

## Фаза 0. Разведка хранилищ

```bash
python scripts/discover.py --repo "<REPO>"
```

Печатает таблицу по всем известным путям: существует ли, тип (JSONL/SQLite), размер,
число файлов, сколько сессий целевого репо. Классификацию инструментов (проверенные
форматы / экспериментальные / неизвестные) и саму карту точек хранения смотри в
`references/storage-layouts.md` — она датируется и дрейфует между версиями.

## Фаза 1. Извлечение (метаданные → нормализованный формат)

```bash
python scripts/extract_codex.py    --repo "<REPO>" --out <OUT>
python scripts/extract_omp.py      --repo "<REPO>" --out <OUT>
python scripts/extract_opencode.py --repo "<REPO>" --out <OUT>
python scripts/extract_zcode.py    --repo "<REPO>" --out <OUT>   # см. ниже про --before-ms
python scripts/extract_claude.py   --repo "<REPO>" --out <OUT>
```

Каждый пишет `<OUT>/data/<tool>_sessions.jsonl` — одна строка на сессию:

```
{ tool, session_id, parent_id, title, directory, t_start, t_end, duration_s,
  n_user_msgs, n_assistant_msgs, n_tool_calls, models[],
  user_messages[{ts, chars, text}],        # полные тексты (до 8000 символов)
  assistant_texts[{ts, chars, head}],      # начала ответов (300 символов)
  tool_calls[{ts, name, call_id, args_head, out_head, exit_code, duration_ms,
              is_error, status}],
  n_errors, errors_head[], tokens{...}, ...специфика инструмента }
```

и `<OUT>/data/<tool>_extract.log`. Инвентарь codex — также `codex_inventory.tsv`.

`session_id` — реальный идентификатор из меты инструмента, не имя файла: у codex
возобновлённые треды = несколько rollout-файлов с общим `session_id`, и
`compute_stats.py` склеивает их автоматически (поля `segments`, `segment_files`).

Опции:

- `extract_zcode.py --before-ms <epoch-ms>` — исключить сессии, созданные позже метки.
  Обязательно используй, когда аудит запускается из того же инструмента над тем же
  репозиторием, чьи логи разбираешь (иначе в выборку попадут сессии самого аудита и его
  субагентов). Для JSONL-инструментов тот же эффект даёт запуск аудита из другого
  репозитория-хоста.
- Все экстракторы: `--limit-sessions N` для быстрой пробы.

## Фаза 2. Количественная статистика

```bash
python scripts/compute_stats.py    --out <OUT>   # все инструменты; склеивает codex-сегменты
python scripts/user_patterns.py    --out <OUT>
python scripts/make_charts.py      --out <OUT>   # опционально, требует matplotlib
```

Выход: `data/stats.json` (обзор по инструментам, таймлайн по дням, профили вызовов,
классификация shell-команд, события ретраев ≥2 одинаковых команд подряд, дайджесты
ключевых сессий в `data/digests/` + `data/digest_index.json`), `data/user_patterns.json`
(классификация запросов, длины, часы активности, корректирующие сообщения),
`data/all_user_messages.jsonl` (корпус с флагами `child`/синтетики). Графики: сессии по
дням, профили вызовов, классификация запросов.

Классификаторы по умолчанию нейтральны к проекту и языку (запросы: RU+EN; shell-команды:
общие категории test/build/git/python/…). Специфику аудируемого проекта передавай
файлами: `compute_stats.py --shell-classes <json>` и `user_patterns.py --classes <json>`
(форматы — в шапках скриптов). Часовой пояс гистограмм берётся локальный; переопределяется
`--tz-hours`.

## Фаза 3. Качественный разбор субагентами (параллельно)

Дайджесты (`data/digests/*.md`) — первичный материал. Разбей ключевые сессии на группы
(по эпохам/инструментам, 4–7 файлов на субагента; ориентир — `digest_index.json`) и
запусти параллельных read-only субагентов. Готовые промпты — 
`references/subagent-prompts.md`; язык отчёта — язык владельца (виден по его репликам в
дайджестах). Если среда без субагентов — читай дайджесты сам, теми же группами и по тем
же вопросам шаблона: методика не меняется, меняется время.

## Фаза 4. Ground truth: escaped defects

Параллельный субагент по самому репозиторию: отчёты валидации/плейтестов (у каждого
проекта своё место — docs/validation, QA-доки, issue-трекер), git-история (сообщения
коммитов часто перечисляют дефекты и находки ревью), бэклоги. Задача: реестр дефектов,
найденных людьми после передачи → таксономия по классам → повторные побеги → слепые зоны
процесса. Шаблон промпта — `references/subagent-prompts.md`.

## Фаза 5. Глубокий причинный синтез (сильная модель + независимая критика)

Финальный документ — не пересказ статистики, а цепочки «Решение → Почему принято →
Последствие → Цена → Кто мог остановить и когда → Что менять». Запускай на самой сильной
доступной модели (в ZCode — динамический workflow с `subagent_model`), с обязательным
раундом независимой критики: второй субагент холодной проверкой ищет безыдоказательные
заявления, пересказ вместо причин, пропущенные паттерны, искажения источников (сверяй с
дайджестами), и автор дорабатывает документ до принятия. Обязательные разделы —
`references/report-template.md`.

## Фаза 6. Сборка отчёта

`<OUT>/report.md`: методика и источники → общая статистика → затыки и систематика →
качественные разборы по эпохам → паттерны взаимодействия → escaped defects → выводы и
рекомендации → приложения. Порядок и состав — `references/report-template.md`. Полные
отчёты субагентов сохраняй дословно в `<OUT>/data/qual_*.md`.

Веб-страница итогов: заполни `<OUT>/data/report_highlights.json` находками Фаз 3–5
(заметки-эпохи по инструментам, топ-затыки, цитаты владельца, волны побегов дефектов,
цепочки «решение → цена»; формат — в шапке `scripts/make_report_page.py` и в
`references/report-template.md`) и запусти:

```bash
python scripts/make_report_page.py --out <OUT>   # -> <OUT>/report.html
```

`report.html` — самодостаточная тёмная страница (инлайн CSS/SVG, открывается локально):
KPI, таймлайн сессий по дням и инструментам, таблица инструментов, retry-топ,
классификация запросов, цитаты, волны побегов. Без highlights-файла страница тоже
соберётся, но только из количественных данных Фазы 2.

Отчёты (`report.md`, `report.html`) НЕ коммитить без решения владельца.

## Чек-лист качества данных (вопросы, которые всплывали на реальном кейсе)

1. **Возобновлённые треды codex** — несколько rollout-файлов на один `session_id`.
   `compute_stats.py` склеивает их по `session_id`. Если пишешь новый экстрактор —
   ключом бери реальный id из меты инструмента, а не имя файла, иначе склейка молча
   не сработает и сессии задублируются.
2. **Служебный трафик доминирует**: у codex внутренние промпты guardian-ревьюера
   одобрений outnumber реальные реплики пользователя в разы. Экстракторы прогоняют
   каждое пользовательское сообщение через `common.is_tool_synthetic` (префиксы
   `<system-reminder>`/guardian-боилерплейт/`<task-notification>`/инъекции продолжения
   + консервативная эвристика длинных мета-промптов, 2+ маркера из BOILER_MARKERS) —
   счётчики `n_user_msgs` в stats.json уже без синтетики, а корпус
   `all_user_messages.jsonl` несёт флаг `synthetic` для перепроверки. Эвристика не
   привязана к языку пользователя, но остаётся эвристикой: после `user_patterns.py`
   проверь `synthetic_filtered` — аномально большая доля значит, что фильтр ест
   реальные сообщения (скрипт сам предупредит). Отделяй child-сессии (промпты запуска
   субагентов) от реального ввода владельца.
3. **SQLite-фильтрация путей**: не полагайся на LIKE для сопоставления директорий — `_`
   и `%` в путях это джокеры, а вложенность LIKE не выражает. Вытягивай `directory` и
   фильтруй `common.matches_repo` в Python (все экстракторы скилла так и делают). Любой
   остальной SQL — всегда параметризуй.
4. **Длительность сессии ≠ время работы**: «настенные» часы включают простои открытых
   сессий (зафиксированы паузы по 7–11 ч и треды, открытые днями). Плотность работы
   оценивай по числу вызовов инструментов.
5. **Метрики ошибок несопоставимы между инструментами**: у одних — статус вызова,
   у других — эвристика по тексту (завышено: «ErrorActionPreference» в тексте скрипта —
   не ошибка). Всегда описывай метод подсчёта в отчёте и приводи оговорку. Стоимость
   (`cost_usd`) показывается только для инструментов, которые её отчитывают; список
   остальных — `stats.cost_untracked_tools`.
6. **Исключай сессии самого аудита** (timestamp-отсечением `--before-ms`), если аудит
   идёт тем же инструментом над тем же репо, чьи логи разбираешь.
7. **Ассистентские тексты и статусы ошибок** у части инструментов лежат в `state.error`,
   а не в `output` — заголовки ошибок могут быть пустыми при верном счётчике.
8. **Секреты в дампах**: `args_head` shell-вызовов содержит командные строки с токенами
   и ключами. Прежде чем цитировать что-то из дампов в отчёте — проверь цитату глазами.
9. Каждое существенное числовое утверждение в отчёте — из `data/*.json`/`.jsonl`,
   а не из памяти; ссылки на файлы данных сохраняй в приложениях.
